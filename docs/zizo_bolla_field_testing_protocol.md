## 1. الأركان السبعة الحاكمة لدستور زيزو وبولا (`SKILL.md`)

### 1️⃣ البنية والمعمارية أولاً (`Core Architecture & SRE Over Script Fluff`)
يركز الاختبار الميداني بنسبة 100% على صلابة البنية التحتية واستقرار النظم الموزعة قبل أي تفاصيل سكربتية عابرة:
1. **سلامة محرك الحالات (`StateStore`):** معاملات `SQLite WAL` الذرية، `PRAGMA busy_timeout=10000`، وعقود الإيجار المفصولة بالحقبة (`Epoch Fencing`).
2. **صمامات التعافي من الكوارث وانقطاع الكهرباء (`Crash Recovery & Orphaned Leases`):** تحرير الجلسات اليتيمة تلقائياً بفحص حيوية معرّف العملية (`owner_pid`) ونبض القلب (`heartbeat_at`) دون المساس بالسلوتات الحية الأخرى، والمرور الإلزامي عبر `RECOVERY_REQUIRED -> RECONCILING -> READY`.
3. **عزل الأسرار وحوكمتها (`LocalSecretVault / Zero Secrets Leak`):** حفظ بيانات الدخول والبروكسيات داخل خزنة `0600` حصراً مع حجب تلقائي عبر `Redactor` وحذف رسائل الإضافة الخام من محادثة التليجرام (`deleteMessage`).
4. **التحكم السحابي عن بُعد (`Telegram Bot API / BoundedOutbox`):** إدارة الأسطول وإضافة الحسابات والمصالحة عبر أوامر محكومة بصلاحيات `RBAC` صارمة (`Default-Deny`).

### 2️⃣ الاختبار خطوة بخطوة بالترتيب (`Strict Step-by-Step Isolation`)
* يُحظر فتح جبهات متعددة في آنٍ واحد أو القفز فوق المراحل.
* كل جلسة فحص تستهدف عقدة معمارية محددة بالتسلسل الصارم:
  `git pull origin main` $\rightarrow$ `pytest tests/` $\rightarrow$ `live-probe` $\rightarrow$ `attach-bot` (مراقبة بالعين المجردة دون لمس الماوس).

### 3️⃣ التقارير التشخيصية المحايدة دون فرض حلول برمجية (`Prescription-Free Diagnostic Reports`)
* يصدر المراجع الميداني تقريراً تشخيصياً يحتوي حصراً على: **العَرَض المشاهد، الدليل الحرفي باللوجات والسطور، الملفات المرتبطة المحتملة، والفرضيات التحليلية**.
* تبقى ملكية تصميم الحل الهندسي الجذري وتنفيذه واختباره في المستودع للوكيل المنفذ (`Implementing Agent`) عبر دفعات `PR` نظيفة ومفحوصة.

### 4️⃣ صفر تدخل يدوي، بوابة الاختبارات الحديدية، وحظر التجويد (`Zero-Touch, Test-Gate & Surgical Scope`)
* **صفر نقرات ماوس:** يعمل العميل ذاتياً بنسبة 100% (تفعيل الجري، تجهيز الطعام، فتح الأبواب، الإيداع البنكي، والتعافي من الكراش).
* **بوابة الاختبارات الحديدية (`Test-Gated Acceptance`):** لا يُعتمد أي كود على الإطلاق إلا بعد نجاح حزمة الاختبارات التراكمية كاملة بنسبة 100% (`pytest` — ضمان عدم كسر المرحلة 1 و2 أثناء بناء المراحل اللاحقة).
* **النطاق الجراحي وحظر التجويد (`Zero Unrequested Tampering`):** يُحظر قطعاً تعديل أي ملف أو كلاس أو دالة قديمة تعمل بنجاح خارج النطاق المطلوب صراحةً، كما يُحظر الترقيع المحلي خارج دورة `git pull origin main`.

### 5️⃣ محرك المحركات والتطور العمودي (`Engine-Level Architecture vs Script Sprawl`)
* عدم الغرق في تفاصيل مراحل البوتات الفردية (صيد، طبخ، تعدين) باعتبارها كبسولات مهام قابلة للتبديل والإزالة (`Pluggable Capsules`).
* تتركز اختبارات الصلابة والهندسة على **المحركات المركزية الستة (`The Six Core Engines`)**:
  1. **محرك الملاحة وحل المسارات (`Navigation Engine`):** توجيه آمن ومقيد بقدرات الحساب في كافة مناطق وطوابق اللعبة.
  2. **محرك الأمان ومراقبة الحياة والحماية التفاعلية (`Safety Watchdog Engine`):** مقاطعة فورية للأكل والإنقاذ والانسحاب عند الخطر دون انتظار ساكن.
  3. **محرك آلة الحالات وعقود الإيجار والتعافي من الانهيار (`FSM & Atomic Lease Engine`):** ضبط التحولات الـ 13، عزل الحقب الزمنية، وفك الحجوزات اليتيمة بعد انقطاع الكهرباء.
  4. **محرك قراءة الواجهات ومربعات الحوار الديناميكية (`Widget & Dialog Engine`):** التعامل المرن مع الحوارات، قوائم الإنتاج (`Make-All`)، ونوافذ ترقية المستويات دون إحداثيات شاشة صلبة.
  5. **محرك التخزين والخزنة المشفرة والدفتر المالي (`Vault & Ledger Engine`):** عزل الأسرار (`0600`) وحساب صافي أرباح وضرائب البورصة (`GE`) وحماية أدوات المهام.
  6. **محرك الاتصال والبروكسيات وعزل السلوتات (`Socks5 & Multi-Slot Engine`):** ربط كل سلوت ببروكسي وساندبوكس معزول بمفتاح قطع فوري (`Fail-Closed Kill-Switch`) ومنع عدوى الأعطال بين الحسابات.
* **التطور العمودي (`Vertical Evolution`):** تعميق وتحصين المحركات الستة المركزية لتستوعب أي سيناريو، بدلاً من التوسع الأفقي الفوضوي بسكربتات مكررة ومرقعة.

### 6️⃣ حلقة الحسابات المفتوحة والشفاء الذاتي (`Dynamic Any-Level Fleet & Self-Healing Loop`)
* **استيعاب أي حساب بأي مستوى (`Any-Level Dynamic Profiling`):** سواء كان الحساب جديداً (`Level 3`) أو مشتراً جاهزاً (`Level 50 .. 100+`، `F2P` أو `Member`)، تفحص النواة بروفايل مهاراته ونقاط مهامه وأدوات بنكه ورصيده تلقائياً، وتوجهه للمهمة الأمثل لجمع الذهب (`GP`) من بين أكثر من **`180` سكربتاً/مهمة** متاحة.
* **التشغيل المستمر المفتوح وعزل الأعطال (`Continuous Open-Loop & Blast-Radius Isolation`):** لا يتوقف الحساب نهائياً بمجرد انتهاء مهمة صغيرة، بل يدور ديناميكياً بين المهام والاستراحات البشرية وتبديل الحسابات بسلاسة دون إهدار للوقت؛ وإذا تعثر حساب واحد (انقطاع بروكسي، طلب `2FA`، أو موت) يُعزل وحده فوراً دون إيقاف بقية الأسطول، وتعالج المنظومة نفسها ذاتياً عبر تحديثات اللعبة وانقطاعات الطاقة.

### 7️⃣ بروتوكول الوكيل المزدوج المعماري (`Dual-Agent Vertical Gateway`)
تُحسم إدارة التطوير بعزل صارم للمسؤوليات دون أي تعارض (`Zero Role Conflict`):
1. **المراجع الميداني — العين الحارسة (`Gemini Flash` على `Antigravity`):** يمثل عين المنفذ الفيزيائية الحية داخل عالم اللعبة، يرصد السلوك الفعلي، اللوجات بالسطور، والحالات غير المتوقعة في محرك اللعبة بدقة المليمتر، وينقل الصورة الكاملة للمنفذ دون لمس الكود.
2. **المنفذ المعماري — المبرمج النظيف (`Arena AI` على `GitHub`):** يصمم ويكتب الشفرة المحصنة على مستوى المحركات الستة عبر دفعات `Clean PRs`، مقيداً ببوابة الاختبارات الصارمة (`61+ passed`) وبحظر العبث أو التجويد في أي كود مستقر يعمل خارج نطاق المهمة.

## 2. المسار التنفيذي الميداني القياسي (`WORKFLOW.md`)

```powershell
# 1. سحب أحدث نسخة معتمدة من المستودع الرسمي
git pull origin main

# 2. التحقق الهرمتي الإلزامي (نجاح 100%)
python -m pytest -v

# 3. مصالحة أي جلسات يتيمة بعد إعادة التشغيل (اختياري — يتم تلقائياً أيضاً داخل attach-bot و status)
python -m osrs_ee reconcile --account-id acc_02 --port 8081

# 4. فحص العميل السلكي القرائي
python -m osrs_ee live-probe --port 8081 --account-id acc_02

# 5. إطلاق المراقبة الحية الذاتية (Zero-Touch)
python -m osrs_ee attach-bot --account-id acc_02 --recipe-id stage2_stronghold_10k --port 8081 --require-food-count 6 --max-ticks 3500
```

## 3. خريطة المراحل الثلاث لبلوغ الأسطول الذاتي (`Fleet Roadmap`)

1. **المرحلة 1 (`Single Autonomous Slot`):** حساب فردي متكامل ينهي المهمة من البداية للنهاية، يودع الغنائم في البنك، ويغلق الجلسة ذاتياً بنظافة.
2. **المرحلة 2 (`Telegram Control Plane`):** تحكم وإدارة كاملة عبر التليجرام (`/add_account`, `/accounts`, `/status`, `/reconcile`, `/pause`, `/drain`, `/abort_all`) مع إشعارات ذكية عبر `BoundedOutbox`.
3. **المرحلة 3 (`Parallel Multi-Account Fleet`):** تشغيل أسطول متوازٍ (`3–4` حسابات على منافذ `8081..8084` وسلوتات `0..3`) بفترات إقلاع متدرجة (`>= 90s`)، استراحات بشرية (`MicrobreakCoordinator`)، وتشتيت مكاني وبروكسي مستقل لكل حساب نشط.
